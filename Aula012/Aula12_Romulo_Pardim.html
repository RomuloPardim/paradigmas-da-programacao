1.1 Por que proximo_id("A") devolve valores diferentes para a mesma entrada? Por que isso dificulta os testes (p. 637)?
Porque a função utiliza uma variável global chamada contador, que é incrementada a cada chamada. Assim, mesmo recebendo o mesmo parâmetro, retorna valores diferentes. Isso dificulta os testes porque o resultado depende do estado anterior do programa, tornando necessário controlar ou reiniciar o contador.
1.2 compor(f, g)(4) e compor(g, f)(4) deram valores diferentes. Calcule os dois à mão e explique a diferença.
Em compor(f, g)(4), primeiro calculamos g(4) = 3 × 4 = 12, depois f(12) = 12 + 2 = 14. Já em compor(g, f)(4), primeiro calculamos f(4) = 4 + 2 = 6, depois g(6) = 3 × 6 = 18. A diferença ocorre porque a ordem de aplicação das funções altera o resultado.
1.3 Qual é a diferença entre sorted(notas) e notas.sort()? Qual dos dois segue o estilo funcional, e por quê?
sorted(notas) cria uma nova lista ordenada sem alterar a original. Já notas.sort() modifica diretamente a lista existente. O sorted() segue melhor o estilo funcional porque evita modificar o estado original dos dados.

2.1 Para que serve o apóstrofo (')? O que o Scheme tentou fazer com (A B C) quando ele não estava lá?
O apóstrofo serve para indicar que uma expressão deve ser tratada como dado, sem ser executada. Sem ele, o Scheme tenta interpretar (A B C) como uma chamada da função A, recebendo B e C como argumentos. Como essa função não foi definida, ocorre um erro.

3.1 No passo a passo, o que cresce na recursão comum e não cresce na recursão em cauda? Por quê?
Na recursão comum, cresce a quantidade de chamadas pendentes na pilha de execução, porque ainda existem operações que precisam ser realizadas após cada retorno. Na recursão em cauda, a chamada recursiva é a última operação, permitindo que linguagens com otimização de cauda reutilizem o mesmo espaço na pilha.
3.2 Por que o Scheme fez um milhão de chamadas e o Python parou com RecursionError? (Dica: releia o quadro sobre a otimização da chamada em cauda e a mensagem de erro do Python. O livro fala do Scheme na p. 656.)
Porque o Scheme garante o tratamento adequado das chamadas em cauda, evitando o crescimento contínuo da pilha. O Python não realiza essa otimização, fazendo com que cada chamada ocupe um novo espaço até atingir o limite de recursão e gerar RecursionError.

(define (tamanho lis)
  (if (null? lis)
      0
      (+ 1 (tamanho (cdr lis)))))

; 2) Soma dos quadrados
(define (soma-quadrados lis)
  (if (null? lis)
      0
      (+ (* (car lis) (car lis))
         (soma-quadrados (cdr lis)))))

; 3) Apenas os numeros pares
(define (pares lis)
  (cond
    ((null? lis) '())
    ((even? (car lis))
     (cons (car lis) (pares (cdr lis))))
    (else
     (pares (cdr lis)))))

5.1 Como o Haskell consegue imprimir parte de uma lista infinita? E por que primeiro 42 (div 1 0) não deu erro de divisão por zero?
O Haskell utiliza avaliação preguiçosa, calculando apenas os elementos necessários. Assim, take 5 squares avalia somente os cinco primeiros elementos da lista infinita. A expressão primeiro 42 (div 1 0) não gera erro porque a função utiliza apenas o primeiro argumento, e o segundo não precisa ser avaliado.

A correção é interromper a procura quando o elemento atual ultrapassar o valor buscado, pois a lista está em ordem crescente. member b [] = False member b (a:x) | a == b = True | a > b = False | otherwise = member b x member 16 squares = True member 17 squares = False

8.3 Qual é o erro de impressão, e como corrigir? O que a mensagem do compilador diz sobre o tipo que ele inferiu?
O erro está na expressão b <- h, que deveria ser b <= h. Em Haskell, <- é utilizado como gerador de elementos de uma lista nas compreensões, enquanto <= é o operador de comparação. O compilador interpreta incorretamente h como uma lista, quando deveria ser o elemento usado como pivô. Isso gera uma incompatibilidade de tipos, pois o programa tenta usar esse valor tanto como lista quanto como elemento comparável.
